# GitEdge design system

A compact interface for working with code. The system keeps the repository-first visual language of [gitea-clone](https://github.com/jan-mue/gitea-clone): restrained surfaces, dense navigation, split repository actions, file rows, and clear status colors. It incorporates GitEdge's live API-backed controls, repository browsing, activity charts, loading transitions, and accessible primitives.

## Foundations

- **Color:** use role-based tokens from `src/design-system/tokens.css`. Every surface has a matching foreground. `success` means open or created, `destructive` means deletion or failure, `warning` means attention, and `merged` identifies merged pull requests. Language identities are centralized `--language-*` visualization tokens.
- **Typography:** Inter for the interface; JetBrains Mono for paths, SHAs, commands, and code. Page titles use 24px bold, sections 18px semibold, controls 14px, and metadata 12px.
- **Spacing:** use the 4px scale. Compact repository controls are 32px high; regular form actions are 36px. Page layout uses a shared 1280px container, 16px horizontal padding, and 24px section gaps.
- **Surfaces:** background → card → secondary/accent. Borders separate dense content; shadows belong to floating overlays. The default radius is 6px.
- **Themes:** dark is the default. Use the toolbar theme selector to inspect the same tokens in light mode. The manager remains dark, inspired by Grafana's component catalog.

## Component contract

Import public components from `@/design-system`. Use named `variant`, `size`, `appearance`, and state props. Public controls deliberately omit `className` and `style`; add layout wrappers when spacing is needed. Routes compose `Page`, `PageHeader`, `Section`, and authentication layouts without custom CSS.

```tsx
import { Button, Page, PageHeader } from "@/design-system"

<Page>
  <PageHeader title="Repositories" actions={
    <Button variant="success" loading={isPending}>Create repository</Button>
  } />
</Page>
```

The underlying shadcn files are generated/vendor primitives and stay untouched. The design system owns all application customizations. Biome's `noTailwindRawColors` rule rejects palette utilities. The repository's AST lint rules prevent bypassing the public system, applying style overrides, or reintroducing native styled controls in application features.

## States and accessibility

Inspect the individual stories and the state galleries before changing a control. Filled actions, borders, text, and focus indicators use semantic tokens. Busy buttons communicate `aria-busy` and prevent duplicate actions. Icon-only actions need an accessible label. Use labels, invalid state, and error descriptions for forms. Radix handles focus trapping and keyboard navigation for overlays, selects, menus, and tabs.

Motion respects `prefers-reduced-motion`. Storybook's accessibility panel evaluates each story. Browser verification visits every story in both themes and at desktop and mobile widths, then exercises hover, keyboard focus, password visibility, menus, dialogs, tabs, and form validation.

## Patterns

Patterns show the actual application components with generated MSW handlers and a real TanStack router/query context. Fixtures remain local to Storybook and do not depend on a live backend. Loading, error, and empty stories preserve the behavior added in recent GitEdge work.

## Development and deployment

Run `bun run storybook` in `frontend/` for the catalog, and `bun run build-storybook` for the static build. `frontend/vercel.ts` selects the static build when `DEPLOY_TARGET=storybook`; the default retains the app's backend relationship, Git HTTP rewrite, and SPA fallback. Storybook uses its own Vercel project rooted at `frontend/`, with the deployment target set in that project for preview and production.

If a frontend preview lacks Vercel related-project metadata, set a branch-scoped `VITE_API_URL` to the matching backend preview. The build prefers the related deployment and fails when neither source is available.
